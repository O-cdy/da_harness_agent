# Profile 机制说明 · 迁移到新公司 / 新业务

> 唯一职责：说明业务背景层如何配置化，以及换公司/换业务线时的迁移步骤。
> 版本：v0.1 | 建立：2026-09-22 | 状态：生效

## 为什么需要 Profile

`docs/` 里的方法论、规则、模块职责是**通用的**；但这些东西是**公司特定的**：

本位币、汇率规则与来源表、平台清单、商品主键（NSSKU）、映射表、COGS 边界、收入确认时点、目标口径、客户标识、大促日历。

如果把这些写进核心代码或散落在各模块里，换一家公司就要改代码 —— 那是耦合，不是配置。
**Profile 机制的作用：把这些全部收敛到一个文件，核心模块只认参数，不认公司。**

## 分层

| 层 | 位置 | 是否含公司特定值 | 换公司时是否改 |
|---|---|---|---|
| 通用规则层 | `docs/30-constraints/`、`docs/10-architecture.md`、`AGENTS.md` | 否 | 不改 |
| 通用口径骨架 | `docs/20-domain/metrics.md`（结构、编码、通用约定） | 否（除已标注的条目值） | 不改结构 |
| **业务背景层** | **`config/profile.yaml`** | **是** | **改这一个文件** |
| 凭据与端点 | `.env`（不入库） | 是 | 改 |

## 迁移步骤

1. 复制 `config/profile.yaml` → `config/profiles/<new-profile-id>.yaml`；
2. 按新公司/新业务改 10 组参数（币种汇率 / 数据源平台 / 商品维度 / 收入冲减 / 成本 / 比率 / 目标 / 客户分层 / 大促日历 / 报告）；
3. 把新 profile 内容置为 `config/profile.yaml`（当前生效文件）；
4. 更新 `.env` 的连接与端点；
5. 核对 `docs/20-domain/metrics.md` 中被 profile 引用的条目是否仍适用 —— 若某条目需要覆盖，在 profile 里改值并注明，**不要**在 docs 里另写一份公司分支（那会造成双源）。

## 硬性约束

- **核心代码禁止出现公司名、表名、币种、具体平台名** —— 一律从 profile 读取。
- **禁止用 `if company == xxx` 之类的分支** —— 遇到差异就抽象成参数，加进 profile。
- profile 只放**值**，不放定义 —— 每个参数必须有 `source` 指向 docs 中的口径条目（守则 2）。
- 新增参数必须同步：profile → `docs/` 对应条目 → 本 README 的参数清单。
