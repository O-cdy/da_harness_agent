## ADR-009 · 2026-09-22 · 指标口径采用双层体系

**决策**：数据可能来自 Shopify、Amazon 及多个第三方平台，口径体系分三层维护：
1. **内部标准口径（canonical）** —— 单源维护于 `docs/20-domain/metrics.md`，是唯一可用于跨源合并与对外报告的口径；
2. **平台官方口径** —— 在同一文件的 B 节记录各平台自己怎么算，附官方文档来源与检索日期，仅用于溯源与对账；
3. **映射关系** —— C 节维护「平台字段 → 内部指标」的转换规则与已知冲突（K-01~K-05）。

**理由**：多平台口径天然不一致（时点、含税含运费、转化率分子、Session 定义、订单/件/order item 层级均不同），只有先统一内部口径才能跨源合并；同时保留平台官方口径，才能在数字打架时快速定位是谁的口径问题。

**被否决**：直接沿用平台口径（跨源不可加总）、只记内部口径不记平台口径（溯源时无法解释差异）。

## ADR-010 · 2026-09-22 · 收入确认时点与退款冲减规则

**决策**：
1. **按下单时点（order time）确认收入**；
2. 退款与取消在**发生月冲减**，**不回溯调整原下单月**；
3. 取消单：不计入订单数、件数与 GMV；
4. 退款单：订单数与件数保留在**原下单月**，退款金额在**退款发生月**冲减净销售额；
5. 由此确立 **G-08 历史月不可变原则** —— 已出报告的历史月数字永不变更。

**理由**：
- 与平台原生数据时点一致：Amazon `Ordered Product Sales = Σ(ItemPrice × UnitsOrdered)` 按下单时点；Shopify `Gross Sales` 亦按下单时点 —— 映射成本最低（K-01）。
- 历史月数字永不变更是「重跑一致、可复现」的硬前提。回溯调整会让上月报告数字随时间漂移，直接废掉 `runs/` 证据包的重跑校验。

**被否决**：
- 按下单时点 + 退款回溯原月（财务最准确，但历史月数字持续变化，需额外维护"重述版本"机制，与可复现目标冲突）；
- 按发货/到账时点（与两大平台原生报表不符，映射需全量重算）；
- 双口径并行 GMV 按下单、收入按发货（复杂度翻倍，二期再议）。

**影响**：`metrics.md` G-03 / G-08 / G-09、M101–M104 状态转为已确认；新增 D-09（GMV 是否含运费）。

## ADR-011 · 2026-09-22 · 本位币 CNY 与 N+1 月度固定汇率

**决策**：
1. **本位币为 CNY**，所有报告默认自动折算到人民币；
2. 汇率由**用户提供**，来源优先级：MySQL `shared_data.exchange_rate` 表 > 用户 Excel（与表同构）；
3. **N+1 规则**：M 月月报用 M+1 月汇率（内部财务规则）；若 M+1 月未结束、库中不存在该月汇率，**回退用 M 月当月汇率**；
4. 缺指定月份汇率时**报错，禁止用其他月份或实时汇率顶替**；
5. 折算必须四元组双留档：`amount_original + currency + fx_rate + fx_rate_month`（G-10）；
6. **例外**：用户特别要求且报告不涉及多市场多币种时，可改用原币（本位币）出报告，须标注「未折算」（G-11）。

**理由**：
- 固定汇率把汇率波动从量价拆解（M401）中剥离，避免"价"的贡献被汇率噪声污染；
- N+1 是内部财务既有规则，沿用而非新造，减少与财务对账的口径差；
- 汇率月份与数值写入证据包，保证重跑一致。

**被否决**：USD 本位币（与内部财务结算规则不符）、订单当日实时汇率（量价拆解失真且不可复现）、分币种不折算（无法出合计与达成率）。

**证据**：`exchange_rate` 表结构（字段：年度月份 / 货币中文名称 / 国家或地区 / 基本货币=CNY / 货币 / 汇率）来自用户提供的库表截图（2026-09-22），已登记 `docs/20-domain/data-sources.md` §5.1。

**影响**：`metrics.md` G-01 / G-02 转已确认，新增 G-10 / G-11；D-01 关闭；`data-sources.md` §5.1–5.2 登记。

## ADR-012 · 2026-09-22 · 成本口径：GMV 不含运费 + COGS 采到岸成本法

**决策**：
1. **GMV 不含运费**（商品口径）；
2. **COGS = 采购成本 + 头程物流 + 关税**（到岸成本）；
3. FBA 配送费 / 尾程物流 / 海外仓操作费归 **M205 履约费率**；仓储费归 **M206 仓储费率**；二者**不进 COGS**；
4. 毛利率分母与分子均为商品口径（不含运费）。

**理由**：
- 到岸成本法是跨境电商主流：毛利反映「货到可售的真实成本」，毛利-费用结构清晰，M203–M206 各费用率**不会与 COGS 重复计算**；
- GMV 与平台原生数据天然对齐 —— Shopify `Gross Sales`、Amazon `Ordered Product Sales` 均不含运费（K-02），映射摩擦最小；
- 与 ADR-010 的下单时点口径无冲突。

**被否决**：
- COGS 仅含采购成本（低客单品类毛利失真，头程占比大时尤其明显）；
- 全成本毛利（含 FBA + 仓储）：更接近单均经济模型，会导致费用率指标与 COGS 重复计算，需重构费用层；
- GMV 含运费：与两大平台原生口径冲突，映射需全量重算。

**影响**：`metrics.md` M101 / M201 / M202 / M205 / M206 转已确认；D-04、D-09 关闭。

## ADR-013 · 2026-09-22 · 月报版本与数据完整度（修订 ADR-010 / ADR-011 的边界表述）

**背景**：ADR-011 落地时我曾补充一条边界——「N+1 汇率行若被更新，旧报告不追改」。该表述**不完整**，与财务实际操作不符，现予修订（原 ADR 不改，以本条为准）。

**实际业务规则（用户澄清）**：
- 9 月未过完时即可生成 9 月经营分析报告 → 当月完整数据尚未产生 → 走**回退规则用 9 月汇率**，产出的是 **partial 版**；
- 到 10 月会**重新生成**一份含完整 9 月数据的月报 → 此时 10 月汇率已存在 → 应按 **N+1 规则用 10 月汇率**，产出的是 **final 版**。

**决策**：
1. 区分两个概念：
   - **重跑（re-run）**：同输入再跑一次 → 结果**必须一致**，用于可复现校验；
   - **重生成（regenerate）**：数据窗口变完整 + 汇率规则变化 → 产出**新版本**，不是修改旧版本。
2. 每次生成都必须按**生成当时**的正确汇率规则取值，**不得**因「上次用了 9 月汇率」就在 10 月沿用旧汇率。
3. partial 与 final 两个版本**并存**，final 不覆盖 partial；报告须显式标注 `data_completeness`（partial / final）与 `fx_rate_month`。
4. G-08 的准确含义收窄为「**报告版本**不可变」，而非「报告月不可变」。

**理由**：汇率是随数据完整度变化的输入，不是被"追改"的历史事实；把重生成误判为回溯修改，会导致 final 版沿用错误汇率，与财务口径脱节。

**影响**：`metrics.md` G-08 措辞修订、新增 G-12；`data-sources.md` manifest 增加 `data_completeness` / `report_version` 字段；月报 playbook 增加版本标注步骤。

## ADR-014 · 2026-09-22 · 退货率双轨、转化率订单口径、新增新老客分层

**决策**：
1. **退货率双轨并列**：M207a 金额口径（退款额 / 净销售额）+ M207b 件数口径（退货件数 / 件数），报表中同时展示；
2. **转化率统一按订单口径**（M210 = 订单数 / Sessions）；Amazon `Unit Session Percentage` 仅作平台原生指标展示，不参与跨品牌对比；
3. 新增 **A5 客户分层类** M501–M506（顾客数 / 新客数 / 老客数 / 回头客率 / 新老客销售额 / 新老客客单价）；
4. **适用硬限制**：新老客分层仅适用于独立站 / 自有渠道；**Amazon 不提供新老客维度**，禁止用其数据计算或合并新老客指标（R-15）；
5. 新增待确认项 **D-10 客户唯一标识口径**（邮箱 / 平台账号 / 手机号去重），是新老客判定的前置条件。

**理由**：
- 退货率单口径必失真：高客单品类一件退货就能把件数率打高，金额率则被低价品稀释，双轨并列才判断得准，且两个数据都已有、成本可控；
- 转化率按订单是 Shopify 原生口径；Amazon 的 `Unit Session Percentage` 按件算可超过 100%（官方示例：1 单 5 件 = 500%），跨品牌不可比（K-03）；
- 新老客分层是独立站长期分析刚需（用户提出），但受平台数据披露限制，必须显式约束适用范围，避免做出"全渠道新老客"这类无法验证的伪指标。

**被否决**：退货率单算金额（掩盖高客单品类问题）、单算件数（被低价品稀释）、转化率按件（与 Shopify 口径冲突）。

**证据**：Shopify 官方口径「新顧客：僅限首購顧客」「回頭客：曾經購買過的顧客」「回頭客比率 = 回頭客 / 顧客數，多數商店 20%–40%」，来源 Shopify 帮助中心 Analytics 數據點參考（检索 2026-09-22）。

**影响**：`metrics.md` M207 拆分、M210 转已确认、新增 A5 节与 D-10；`rules.md` 新增 R-15 / R-16。

## ADR-015 · 2026-09-22 · 首期数据源范围 = Shopify 独立站

**决策**：首期只接入 **Shopify 独立站**；Amazon、第三方平台、自有 ERP 均列为「未接入」。

**理由**：
- 单平台 → 不涉及跨源合并，首期可把精力放在 harness 链路跑通而非口径对齐；
- Shopify 官方口径已核实并登记，映射成本最低；
- 新老客分层（用户长期需求）只有独立站这条路能做，首期接入即可支撑。

**保留项（不为首期简化而删）**：
- **双层口径体系**（ADR-009）保留：内部 canonical 口径 + 平台官方口径 + 映射表；
- **Amazon 官方口径**（`metrics.md` B2）保留登记，未来接入直接复用，无需重新调研；
- **五大跨源冲突 K-01~K-05** 保留为约束（单平台下多不触发），防止后续接入时踩坑；
- **汇率折算（ADR-011）仍然生效**：独立站依然存在多币种 / 多市场。

**影响**：`data-sources.md` §1.1 登记平台清单；D-08 关闭。

## ADR-016 · 2026-09-22 · 目标值来源与达成率口径

**决策**：
1. 目标由**用户提供目标表**（DB 表优先，Excel 亦可，与汇率表同样支持双通道）；
2. 目标维度为 **月 × 站点 × 品类**，三键唯一；
3. 目标口径为 **净销售额（M102）**，与达成率实际值口径一致（R-17）；
4. 目标表快照 hash 入 `source_manifest.json`；
5. 某维度缺目标 → 输出「目标未设置」，**禁止用父级/总量目标按比例下推**（那属于臆造，违反 R-03）。

**理由**：ADR-012 之后所有规模指标都是商品净额（不含运费）。若目标按 GMV 定、实际值取净销售额，达成率会**系统性虚低**且偏差不可解释；口径一致是达成率这个指标唯一有意义的前提。

**被否决**：目标按 GMV 口径（与 M102 不一致，达成率失真）；目标写入配置文档手工维护（无快照、无历史版本，不可追溯）。

**影响**：`metrics.md` M301 转已确认、D-07 关闭；`rules.md` 新增 R-17；`data-sources.md` §5.1b 登记目标表。

## ADR-017 · 2026-09-22 · 新老客主键 = customer_id，游客单单独归类

**决策**：
1. 新老客判定主键采用 **`customer_id`**（Shopify 订单的 customer 关联 ID），不用邮箱/手机号拼接；
2. **`customer_id` 为空的订单（游客结账）归入「未识别」客群，禁止计入新客**（R-18）；
3. 新增 **M507 顾客可识别率**作为数据质量指标（有 `customer_id` 订单数 / 总订单数）；新老客章节必须同时给出 M507；
4. 未识别订单的金额**仍计入总销售额**，只在客户分层中单列。

**理由**：
- Shopify 官方文档明确：buyer identity 的 `customer` 属性「**The value is undefined if the buyer is a guest or hasn't logged in yet**」—— 即游客结账**没有** `customer_id`（证据：Shopify Buyer Identity API 文档，检索 2026-09-22）。
- 若把游客单直接算作新客：老客用游客身份复购会被误判为新客 → **系统性高估新客数、低估回头客率**，结论方向性错误，比样本缺失更危险。
- 用 M507 把偏差显式化，让读者知道这份新老客结论的可信程度，而不是假装数据完整。

**被否决**：邮箱去重（同一人换邮箱仍分裂；且与平台主键不一致）；邮箱+手机号组合（需额外清洗，成本上升，首期不必要）；把游客单算作新客（方向性错误）。

**证据等级**：官方 API 文档（强）+ 社区帖（弱，用于佐证 guest 场景下 customer 字段缺失的处理经验）。

**影响**：`metrics.md` M501–M506 转已确认、新增 M507、D-10 关闭；`rules.md` 新增 R-18。

## ADR-018 · 2026-09-22 · 业务背景层可配置化（Profile 机制）

**背景（用户提出）**：当前所有口径已触及公司层面的业务背景（本位币、N+1 汇率、Shopify、NSSKU、COGS 边界、大促日历……）。若这些写死在核心里，agent 无法迁移到新公司 / 新业务背景。要求：**模块化、低耦合，换业务只改配置文档，不改核心**。

**决策**：
1. 引入 **Profile 机制**：`config/profile.yaml` 为「公司 / 业务背景层」的唯一配置入口，承载 10 组参数（币种汇率 / 数据源平台 / 商品维度与映射链 / 收入冲减 / 成本费用 / 比率口径 / 目标 / 客户分层 / 大促日历 / 报告）；
2. **核心代码禁止出现公司名、表名、币种、平台名**，一律从 profile 读取；**禁止 `if company == xxx` 式分支** —— 遇到差异抽象成参数加进 profile；
3. Profile 只放**值**，不放定义：每个参数带 `source` 指向 `docs/` 中的口径条目，**不复制正文**（守则 2 / 守则 8）；
4. 分层：通用规则层（`docs/30-constraints`、`10-architecture`、`AGENTS.md`）→ 通用口径骨架（`metrics.md` 结构与编码）→ **业务背景层（profile）** → 凭据层（`.env`）；换公司只改后两层；
5. 迁移方式：复制 profile → 改参数 → 置为当前生效文件 → 更新 `.env` → 核对 docs 中被引用条目是否仍适用（需要覆盖时在 profile 改值并注明，**不在 docs 里另写公司分支**）。

**理由**：把业务背景从代码与文档中剥离，是"可直接迁移"的唯一可靠做法；散落的公司特定值会在迁移时漏改，且无法验证改全了没有 —— 收敛到单文件后，迁移的完整性是可检查的。

**被否决**：把公司特定值留在各模块里（迁移必然漏改）、为每个公司建一套 docs 分支（双源过期冲突，违反守则 2）。

**影响**：新增 `config/profile.yaml`、`config/profiles/README.md`；`PROJECT_STATUS.md` 待办新增「profile 参数随业务变更同步」。

## ADR-019 · 2026-09-22 · 净销售额基准字段与退款归属（解决 C-01）

**决策**：
1. **M101 GMV** = Σ(`gross_sales`)，原币，剔除 `cancelled_at IS NOT NULL`；
2. **M102 净销售额** = Σ(`gross_sales` + `discounts`)（`discounts` 在库中已为负数），剔除取消单；
3. **退款不从主表扣**，改由 `bluetti_new.refunds_lineitems.refund_subtotal` 按 **`refund_created_at` 归属退款发生月**冲减；
4. **禁止**用主表 `net_sales` / `returns_amount` / `tableau_sales` 作为内部指标源（R-19）；
5. 未匹配 NSSKU 的 SKU（实测 1.52%）归入「未映射」桶，金额计入总额但不参与 NSSKU 维度聚合（R-21）；
6. 报告「数据说明」章节须给出**与现有 tableau 报表的差额对账**（G-13、R-20）。

**理由**：
- 主表 `net_sales` 已按 `sale_date` **回溯**扣退款（实测：3 月下单、4 月退款会改小 3 月数字）。若直接用它，每次补数据历史月数字都会变，直接废掉 G-08 与重跑一致性。
- 用 `gross_sales + discounts` 基准 + 退款按发生月冲减，站点间口径统一（不存在 `tableau_sales` 那种 US/CA 与其他站点不一致的问题）。

**代价（明确记录）**：内部 M102 **不等于**公司现有 tableau 报表口径，两者差额 = 跨月退款的时间归属差异。这是为保住可复现性主动承担的口径差异，须在报告中显式对账，不得静默混用。

**被否决**：直接用 `net_sales`（与 tableau 一致但违反 G-08，可复现性受损）；双轨并行（报告多一列，口径解释成本上升，首期不引入）。

**证据**：直连核实 2026-09-22 —— 主表 45 列 1,289,508 行；`refunds_lineitems` 46,509 行带 `refund_created_at`，实测跨月退款案例（下单 2026-03-12、退款 2026-04-20）。

**影响**：`metrics.md` M101/M102 落到字段级、新增 G-13；`rules.md` 新增 R-19 / R-20 / R-21；`data-sources.md` C-01 关闭。

## ADR-021 · 2026-09-22 · 订单表分工定案（关闭 B-10）

**背景**：库内存在三套 Shopify 订单数据，原先担心"选错会双计"（B-10）。2026-09-22 直连实测后，该担忧被证伪。

**决策：不做二选一，按职责分工。**

| 用途 | 权威表 | 理由 |
|---|---|---|
| **所有金额类指标**（GMV / 净销售额 / 退款 / 成本 / 达成率） | `bluetti_new.shopify_sales_by_order` | 唯一带 `site` + `currency` + `dedup_fingerprint` + `cancelled_at` 且可映射 NSSKU 的表；是现有财务/BI 加工链的输入 |
| **订单级口径**（订单数 / 客单价 / 取消率） | `bluetti_new.shopify_orders_mongo_total` | 实测 1.002 行/单，天然订单级，无需去重 |
| **补充维度**（UTM / 渠道 / 地址 / 支付网关 / 折扣码 / 履约状态） | `bluetti_new.shopify_orders_mongo` | 主表完全没有这些字段；按 `order_name` ↔ `name` 关联 |
| **退款金额主体** | `bluetti_new.refunds_lineitems` | 有行项明细、SKU、数量，能归 NSSKU 与度数区间（R-20） |

**关键实测依据**（详见 `data-sources.md` §5.3）：
1. **订单集合几乎完全重合** —— 全表按订单号比对，仅 `sales_by_order` 独有 3 单（金额均为 0.00），`orders_mongo` 独有 0 单 → **同源，不存在双计风险**。
2. 先前观察到的 7~8% 差异来自 **`sale_date` ≠ `created_at`**，加月份窗口即产生伪差异（R-23）。
3. 折算 CNY 后 2026-08 差 8.3%，**同币种 USD 只差 1.96%** → 无本质口径冲突，差异源于行级粒度与月份归属。
4. **`orders_mongo.rate` 是税率不是汇率**（USD 0.06/0.01/0.0025/0.0625；JPY 0.1）→ 汇率唯一来源仍是 `exchange_rate`（R-24）。

**附带定案**：跨币种金额**必须先折算再汇总**；任何 `SUM(金额)` 未经折算即跨币种相加的产物一律无效。

**影响**：`rules.md` 新增 R-23 / R-24；`data-sources.md` §5.3 新增「三套 Shopify 订单表的关系」小节；B-10 关闭。C-04（adjustments）不在本条范围内，另行决策。

## ADR-022 · 2026-09-22 · 退款三口径定案（关闭 C-04 / B-09）

**背景**：`refunds_adjustments` 正负成对，原判断为"疑似双重记账、不知该如何纳入"（C-04 / B-09）。查 Shopify 官方文档后语义明确，并以实测验证。

**决策一：`refunds_adjustments` 是「差额科目」不是「退款额」，必须纳入，但必须用正确算法。**

官方定义：`OrderAdjustment` = 「the difference between a **calculated** and **actual** refund amount」；REST Refund 文档补充：差额调整是 Shopify 自动生成的，目的是「account for the discrepancy in the store's **financial reports**」。

即 **计算退款(lineitems) + 差额(adjustments) = 财务报告口径**。实测印证：折算 CNY 后 A+F 与「实际成功退款 C」偏差仅 -3.3% ~ +9.9%，量级完全对齐。

**决策二：两个算法红线。**

1. 必须按（订单 + 退款时刻）**组内取净额**再汇总（R-25）—— 29.4% 的组是完全抵消的成对记账；
2. 必须**先折算 CNY 再汇总**（R-26）—— 实测差额折算后为 **负**（-27万~-36万/月），原币裸和却是 **正**（+119万~+243万/月），**符号被原币颠倒**。

**决策三：退款存在三个口径，报告必须显式声明用哪一个（R-27）。**

| 口径 | 算法 | 特点 |
|---|---|---|
| 计算 | `refunds_lineitems.refund_subtotal` | 可按 SKU / NSSKU / 度数区间归因；含未成功退款 |
| 财务 | 计算 + 差额（组内净额，折算后） | ≈ Shopify 财务报告口径 |
| 实际到账 | `shopify_orders_mongo_refunds` WHERE `status='success'` AND `kind='refund'` | 官方明确"只有 success 才算钱真退了"；**丢失 SKU 明细，无法归因** |

**决策四：新增必报对账项 —— 退款实现率。**
实测 2026-08 有退款行项的 1,046 单中，**114 单（10.9%）无任何 success 交易**。若按计算口径全额冲减，会把未实际退回的钱算成退款 → 低估净销售额。因此月报必须给出「计算口径 vs 实际到账口径」的差额与实现率。

**主口径选择**：待用户定案（推荐`计算`作主口径 + 强制双口径对账），见 `PROJECT_STATUS.md` B-11。

**影响**：`rules.md` 新增 R-26 / R-27；`data-sources.md` §5.3 新增「退款三表与 Shopify 官方对象映射」小节；C-04 / B-09 关闭；新增待决项 B-11。

## ADR-023 · 2026-09-22 · 退款主口径定案（关闭 B-11）+ 数据源约束

**决策一：主口径 = 财务口径。**

- **整体 / 站点 / 达成率**：退款 = `Σ refunds_lineitems.refund_subtotal` + `Σ refunds_adjustments`（组内净额），**均先折算 CNY 再汇总**，按 `refund_created_at` 归属退款发生月冲减（R-20 / R-25 / R-26）。
- **商品维度拆解（NSSKU / 度数区间 / 型号）**：用**计算口径** = `refunds_lineitems.refund_subtotal`。差额部分**不可归因**，在拆解表中单列为「不可归因差额」，不得分摊到商品上。
- 整体数与商品拆解数会因此相差约 7%（差额占比），报告须显式写明（与退货率双轨 M207a/b 的处理惯例一致）。

**理由**：目标表 `market_goal` 是财务口径的净销售额，用同源口径比才不自相矛盾；差额每月 -27万~-36万 CNY（约占退款 7%）不可忽略，忽略会系统性高估。

**决策二：数据源约束（用户指定）—— 主口径不用 `shopify_orders_mongo` 系列。**

金额一律取官方 API 拉取的 `shopify_sales_by_order`；退款取 `refunds_lineitems` + `refunds_adjustments`。

**决策三：由此产生的能力缺口与处置。**

`shopify_orders_mongo_refunds.status` 是库内**唯一**能判断"退款是否真正成功"的字段（`sales_by_order` 与 `refunds_lineitems` 均无此字段）。禁用后：
- 主口径**不受影响**（财务口径不需要 status）✓
- 但「退款实现率」监测失效 —— 实测 2026-08 有 **10.9%**（114/1046）的退款订单无任何 success 交易，该风险将无法被自动发现。

处置：在 `profile.yaml` 增加 `revenue.refund_reconciliation.enable_success_check`（**默认 false**）。开启后仅读取 `shopify_orders_mongo_refunds` 用于**报告对账区**，不进净销售额计算（符合守则 4 的 env 门控 / 无配置即 no-op）。关闭状态下，报告「数据说明」章节必须显式声明「退款实现率未监测」。

**影响**：`rules.md` R-27 更新；`metrics.md` M102 更新；`config/profile.yaml` 新增 `revenue.refund_caliber` 与 `refund_reconciliation`；B-11 关闭（待补 B-06 大促日历）。

## ADR-024 · 2026-09-22 · 首期维度范围定案：不含渠道 / UTM 归因

**决策**：首期月报**不做渠道归因**，维度树限定为 **站点 × 品类 × 度数区间 × NSSKU × 新老客**。

## ADR-025 · 2026-09-22 · 转化率口径定案（M210）

**背景**：用户指出 `bluetti_new.month_basic_data`（视图，GA4 漏斗）可作为独立站流量源，M210 转化率由「不可实现」转为可实现。但实测 GA4 与 Shopify 订单存在系统性差异，需定案口径。

**决策：报告同时给出三个数，主口径为 GA4 同源转化率。**

| 项 | 定义 | 2026-08 US |
|---|---|---|
| **主口径：转化率** | `month_basic_data.transactions / sessions` | **0.364%** |
| 辅助：结账率 | `month_basic_data.checkouts / sessions` | 2.285% |
| 对账项：两源差异率 | GA4 `transactions` / Shopify 订单数 | **36.6%**（合计 52.4%） |

**理由**：
1. 分子分母必须同源 —— GA4 受归因、广告拦截、同意模式影响，2026-08 合计仅覆盖 Shopify 订单的 **52.4%**（US 36.6%、EU 16.8%、JP 23.9%），跨源配比得出的不是转化率而是口径错误（R-37）；
2. 但同源的 0.364% 明显低于行业常态，**若不解释会被误判为"算错了"** → 因此强制同时给出结账率与两源差异率，把 GA4 系统性少计的事实摆在报告里。

**附带数据源原则（R-36）**：用户明确 —— 未维护状态的数据表、mongo 系列、副本 / 备份表**均不纳入使用考虑**（老版本备份遗留）。数据源改为**白名单制**，白名单与禁用清单见 `data-audit.md` §8。

**已知限制**：GA4 数据仅覆盖 **2025-06-09 起**（约 15 个月），早于该日期无转化率；各市场起始日不同（`ie` 105 天、`nz` 76 天）。

**影响**：`metrics.md` M210 更新；`rules.md` R-36 重写为白名单制、新增 R-37 / R-38；`data-audit.md` §8 / §10 更新。

## ADR-026 · 2026-09-22 · 新老客口径定案（M501–M506）

## ADR-027 · 2026-09-22 · 首期数据源收敛为白名单制 + 成本利润类不纳入设计范围

> ⚠ **修订提示**：本条**决策一**（白名单 = 6 张表）**已被 ADR-028 修订为 8 张表**（补入 `refunds_lineitems` / `refunds_adjustments`）。ADR 只增不改，原文保留留痕；**执行一律以 ADR-028 为准**。决策二（成本利润类不纳入设计范围）与决策三中除 B-13 外的部分**未被修订，仍然有效**。

**背景**：用户要求严格限制数据源，首轮开发只用指定 6 张表；成本利润等敏感指标先不纳入设计范围；`market_goal_bonus` 不需要理会。

### 决策一：首期数据源白名单 = 6 张表（其余一律不可用）

| # | 表 | 用途 | 实测规模（`COUNT(*)` @ 2026-09-22） |
|---|---|---|---|
| 1 | `bluetti_new.shopify_sales_by_order` | 销售事实（金额 / 订单 / 件数 / 站点 / 币种 / 客户 gid） | 1,289,508 行 |
| 2 | `bluetti_new.market_goal` | 目标（年月 × 站点，CNY 万元） | 916 行 |
| 3 | `shared_data.exchange_rate` | 汇率（N+1 规则） | 1,169 行 |
| 4 | `bluetti_new.month_basic_data`（视图） | GA4 漏斗 → 转化率 | 8,149 行 |
| 5 | `shared_data.产品型号度数范围` | 度数区间维度 | 210 行 |
| 6 | `shared_data.nssku对应映射表` | SKU → NSSKU 映射 | 73,858 行 |

**首期一律不得读取**（即便 ADR-021/022/023 曾提及）：`shopify_customers_by_site`、`repurchase_user_sku_stats`、`refunds_lineitems`、`refunds_adjustments`、`shopify_orders_mongo*`、全部 `*_copy*` / `*_backup*` / `*_old_*` 副本备份表（R-36）。

**`market_goal_bonus` 列入「不理会清单」**（用户 2026-09-22 明确「不需要理会」）：不在白名单、也不单列禁用条目，**首期一律不读**。若后续要用，必须另立 ADR。

### 决策二：成本 / 利润 / 毛利类指标不纳入**设计范围**

M201 毛利 / M202 毛利率 / M203 平台佣金率 / M204 广告费率 / M205 履约费率 / M206 仓储费率，以及 ADR-012 定下的 COGS 到岸成本口径 —— **首期不做设计**（不是「数据源未接入所以暂不输出」，而是**不进入设计范围**：不定义、不建模型、不留空占位、不在报告中留标题）。

R-03 仍然生效：**不估算、不插值、不用行业均值填充**。

**理由**：① 两库无成本字段，本来就不可实现；② 属敏感指标，业务口径未授权前不设计，避免后期推倒重来。

### 决策三：首期可实现指标范围（明确记录）

| 类 | 指标 | 状态 |
|---|---|---|
| 规模 | M101 GMV / M102 净销售额 / M103 订单数 / M104 件数 | ✅ 可实现 |
| 效率 | M105 客单价 / M106 件单价 / M210 转化率 | ✅ 可实现 |
| 达成 | M301 达成率 / M302 缺口 / M303 贡献度 | ✅ 可实现（**受 B-13 影响，见下**） |
| 异动 | M401 同比环比 / M402 异常检测 | ✅ 可实现 |
| 客户 | M501–M507 新老客分层 | ✅ **可实现，不受影响** |
| 效率 | M207a / M207b 退货率 | ⚠ **受 B-13 影响** |
| 成本利润 | M201–M206 | ❌ 不纳入设计范围（决策二） |

**M501–M507 为何不受影响**：R-35 的主键 `shopify_customer_gid` 与 R-39 的 `MIN(sale_date)` 首单月**都在 `shopify_sales_by_order` 内**，不依赖 `shopify_customers_by_site`。实测销售表 gid 唯一 435,643、客户表匹配率 99.96% → 用主表即可闭合。

### 决策四：由此产生的缺口 —— **B-13 退款冲减缺口（待用户决策）**

排除 `refunds_lineitems` / `refunds_adjustments` 后，产生三处连锁影响（实测证据）：

| 影响面 | 说明 | 量级 |
|---|---|---|
| M102 净销售额 | ADR-019 要求退款按 `refund_created_at` 发生月冲减 → 无退款表则**只能输出毛口径**（`gross_sales + discounts`，未扣退款） | 系统性高估 |
| **M301 达成率** | 目标口径 = **净销售额**（ADR-016 / ADR-020），分子若改毛口径 → **分子分母口径不一致** | 高估约 **5.84%** |
| M207a / M207b 退货率 | 分子（退款额 / 退货件数）全部来自退款表 | 不可实现 |

**实测支撑（2025-10 ~ 2026-09，全币种按当月汇率折算 CNY）**：

```
销售额合计  897,077,743 CNY
退款合计     52,398,746 CNY   →  占比 5.84%
USD 单币种：46,257,435 / 2,182,040 → 4.72%
月度波动：2025-10 = 10.13%   2025-11 = 2.51%   2026-07 = 7.46%   2026-09 = 2.98%
```

→ 达成率若用毛口径，不仅整体高估约 5.8 个百分点，**月度波动还会造成趋势失真**（相邻两个月差异可达 7.6pp，足以把"达成率下滑"误判为"改善"）。

**本 ADR 不解决 B-13**，待用户二选一后另立 ADR-028：① 把 `refunds_lineitems` + `refunds_adjustments` 补进白名单（共 8 张）；② 维持 6 张，首期达成率改按毛口径并在报告显著位置标注「未冲减退款，与目标口径不一致」。
**默认（未决策前）按 ② 执行并显式标注**，不静默混用。

**影响**：`rules.md` 新增 R-41 / R-42；`data-audit.md` §8 白名单改为两档；`metrics.md` M201–M206 标注「首期不纳入设计范围」；`config/profile.yaml` 新增 `datasource.first_phase_whitelist` 与 `metrics.excluded`；`PROJECT_STATUS.md` 新增 B-13、§14.1 关闭。

## ADR-028 · 2026-09-22 · 退款两表补入首期白名单（关闭 B-13，修订 ADR-027 决策一）

**背景**：ADR-027 把首期白名单限定为 6 张表，由此产生 **B-13 退款冲减缺口**——M102 无法按 ADR-019 冲减退款，M301 达成率分子分母口径不一致（高估约 5.84%），M207a/b 退货率不可实现。

用户追问两点后确认放行：
1. 「退款表有没有日常维护更新？」→ 实测：**有**。见下。
2. 「退款表名称是什么？我之前说过 mongo 的表不纳入吧？」→ 澄清：库内有**两套**带 `refund` 的表，性质完全不同：

| 表 | 系列 | 状态 |
|---|---|---|
| `bluetti_new.refunds_lineitems` | **官方 API 独立表** | ✅ 本次补入白名单 |
| `bluetti_new.refunds_adjustments` | **官方 API 独立表** | ✅ 本次补入白名单 |
| `bluetti_new.shopify_orders_mongo_refunds` | **mongo 系列** | ❌ 仍禁用（R-28 / R-36） |
| `bluetti_new.shopify_orders_mongo` / `_total` | **mongo 系列** | ❌ 仍禁用（R-28 / R-36） |

**判别口径**：表名含 `orders_mongo` → 禁用；以 `refunds_` 开头且不含 `mongo` → 官方 API 表，未被禁用。ADR-023 决策二原文即为「退款取 `refunds_lineitems` + `refunds_adjustments`，不用 `orders_mongo` 系列」。

**维护状态实测（2026-09-22 17:20，`data-audit.md` §8.3）**：

| 项 | `refunds_lineitems` | `refunds_adjustments` | 对照 `shopify_sales_by_order` |
|---|---|---|---|
| 最新时间 | **2026-09-21 21:38:31** | **2026-09-21 09:59:19** | **2026-09-21 20:51:28** |
| 近 18 个月断档 | 无 | 无 | 无 |
| 月度行数区间 | 564 ~ 2,091 | 121 ~ 4,948 | 22,450 ~ 56,366 |

→ **持续写入的活表，与销售表同日同步**，不属用户排除的「未维护 / mongo / 副本备份」任一类。

**决策**：
1. **首期白名单 6 → 8 张**，补入 `refunds_lineitems` 与 `refunds_adjustments`（R-41 已修订）。
2. **M102 恢复 ADR-019 / ADR-023 定案口径**：Σ(`gross_sales` + `discounts`)，退款按 `refund_created_at` 发生月冲减；整体/站点/达成率用**财务口径**（lineitems + adjustments 组内净额、折算后汇总），商品拆解用**计算口径**（差额单列不可归因）。
3. **作废临时口径 M102b**（毛口径）—— 仅保留一条作废留痕，不进实现。
4. **M301 达成率恢复口径一致**：分子分母同为净销售额，撤销「高估 5.84%」的标注要求。
5. **M207a / M207b 退货率恢复可实现**。
6. **新增监控项**：`refunds_adjustments` 月度行数波动大（2025-10 仅 121 行 vs 2026-07 达 4,948 行）。若某月行数归零或环比骤降 >80%，须告警并显式标注「差额科目疑似未采集」—— 该表是 Shopify 自动生成的差额科目，波动正常，但归零属异常。

**仍不可知（明确记录）**：数据只能证明「在被持续写入」，**无法证明采集管道有运维责任方**。确认需问数据提供方。

**影响**：`rules.md` R-41 修订；`data-audit.md` §8.1 补 2 张、§8.2 移除退款行、§14.5 关闭；`metrics.md` M102 恢复、M102b 作废、M301 / M207a / M207b 撤销 B-13 标注；`config/profile.yaml` 白名单补 2 项；`PROJECT_STATUS.md` **B-13 关闭**。

## ADR-029 · 2026-09-22 · 开工前商品双路径与实现契约收口

> **状态：未对齐 · 不作为硬约束**（2026-09-23 用户要求撤回。ADR 只增不改，原文保留。以 **ADR-030** 为准：SSOT 已回滚，本条内容全部 **待对齐**，实现禁止引用。）

**背景**：用户补齐商品挂载规则；独立 agent 直连复核发现「文档宣称已对齐但 `profile.yaml` 未改」、M103 公式引用不存在的 `order_id`、NSSKU 一对多 naive JOIN 会打爆金额、无大促日历时 R-12 会阻断整份月报。本条在写代码前把契约钉死，防止返工。

### 决策一：事实表粒度与商品双路径（用户指定）

- 事实表 = `bluetti_new.shopify_sales_by_order`。**一行 = 一个销售 SKU**（不是订单头）。
- 挂载键：销售 SKU = `nssku对应映射表.名称`。
- **经营要金额 / 月报规模与达成**：按 `名称` 去重，型号取 `MAX(型号)`，**禁止**把套件成员行展开后对金额求和（实测 18,425 / 48,404 个名称一对多，最大 10 行）。
- **复购要路径**：按成员展开；台数 = `quantity × 成员数量`。台数 ≠ M104 件数。首期月报**不输出台数、不读复购表**（R-41 仍排除），本规则只作后续复购场景的预留契约。
- 桥接度数范围表：`LOWER(TRIM(MAX(型号))) = LOWER(TRIM(产品型号))`。`产品型号_统一` **只作成品标签，不作 JOIN 键**（实测 `PV350` 会同时命中 `pv350` 与 `350w`）。

### 决策二：品类 / 度电带 / 户储的来源（用户指定）

一律来自 `shared_data.产品型号度数范围`，**禁止**用 `nssku对应映射表.子类型`。

| 业务标签 | 源列 | 实测备忘 |
|---|---|---|
| 品类 | `产品类型` | 储能 / 太阳能板 / 电池 / 冰箱储能 / 房车系统 / 阳台光伏 / cpap储能 / cpap电池 / 冰箱 |
| 度电带、户储标签 | `度数范围` | 「户储」「阳台电站」是该列的取值，不是独立列；储能还有 `0.5度电-` … `3度电+` |
| 归一型号 | `产品型号_统一` | 如 `el300`；与 `MAX(型号)` 经 `产品型号` 桥接后读取 |

未命中度数范围表 → 进「未映射」桶（R-21），金额仍计入总额，不参与品类/度电带/户储聚合。

### 决策三：汇率、目标、退款原因（用户指定，与既有 ADR 对齐）

- CNY 折算唯一源 = `shared_data.exchange_rate`；**销售月优先下一个月汇率**（即既有 N+1，ADR-011），缺 M+1 回退当月，再缺则报错。
- 目标唯一源 = `bluetti_new.market_goal`（年月 × 站点，CNY 万元，R-22）。
- **退款原因只有** `refunds_lineitems.financialStatus`。禁止用 `refunds_adjustments.adjust_reason`、`cancel_reason` 或 mongo 交易状态充当退款原因。实测取值：`refunded` / `paid` / `partially_refunded` / `voided` / `pending` / `partially_paid`。

### 决策四：独立复核后的实现契约（防止写代码时抄错）

| 项 | 契约 |
|---|---|
| 订单键 | M103 = `COUNT(DISTINCT order_name)`。销售表无 `order_id`。退款关联 = `refunds_lineitems.name` = `order_name` |
| 支付状态 | 计入经营：`PAID` / `REFUNDED` / `PARTIALLY_REFUNDED`，并仍剔除 `cancelled_at IS NOT NULL`。其余状态进异常桶，不进 M101–M104 |
| 草稿单 | `source_name='shopify_draft_order'` **计入**经营，报告数据说明须披露行数；剔除须另立 ADR |
| 站点映射 | 只写在 `config/profile.yaml` 的 `site_code_map`（`NG↔NGA↔nga`）；**不读** `国家对应表`（不在白名单）。`南亚` / `众筹` / 站点 NULL 排除出站点维 |
| EU ≠ 欧盟汇总 | `site=EU`（店铺 `bluettipower-de`）与 `DE`/`FR`/`IT`/`ES` 是不同店，订单名零重叠；禁止把 EU 当成四国合计 |
| 冷启动 | 站龄不足 12 个完整月（IE/NZ/SA 等）**不参与同比**，可出环比并标注「新站」 |
| 无日历 | SK-03 / R-12：**不阻断**规模 / 效率 / 达成；异动章必须标注 `calendar_missing=true`，不得把未识别窗口的下跌写成经营恶化 |
| 固化月报 SQL | 必须有时间窗谓词；**允许**无 LIMIT 的全表扫描。R-04 的 LIMIT 约束只约束探索/ad-hoc 路径 |
| C1/C2 | 月报 playbook 模板首次人工放行后，同模板+同口径版本可自动放行；改 SQL 模板或口径版本才再审 |
| 双库 | 事实库 `bluetti_new` + 维表库 `shared_data`，env 分项配置，禁止只配一个 `MYSQL_DATABASE` |
| M208/M209 | 随 M201–M206 **不纳入首期**（R-42 覆盖净利） |
| G-04 / G-05 | 首期默认：认 `sale_date`（已是 date）+ 自然月；报告标注。不阻塞开工 |
| 转化率对账 | GA4 vs Shopify 订单差异率的分母 = **未取消**的 `COUNT(DISTINCT order_name)`；PH 无 GA4 market → 该站转化率输出「无数据」 |
| `market_goal.实际销售额` | 禁止作交叉验证（2026-08 全空；历史月有值也不用） |

**被否决**：① 经营金额按成员展开；② 用 `nssku.子类型` 当品类；③ 无日历就整报失败；④ 把「文档写了已对齐」当作配置已改（见 E-0005）。

**影响**：`metrics.md` G-04/G-05/G-14/G-15、M103/M104/M207/M208；`rules.md` R-04/R-12/R-21/R-31/R-42 修订 + R-43~R-48；`data-sources.md` / `data-audit.md` / playbook / 架构 / skills / `profile.yaml` / `.env.example` 就地改；不新建规划文档。

## ADR-035 · 2026-09-23 · 型号挂在 NSSKU 上；店铺 SKU 与型号不同级

**背景**：用户复核 ADR-034 维度树：型号是 NS 维才有的属性；一个店铺 SKU 可含多个 NSSKU（例如储能 + 太阳能板），店铺 SKU 不能和型号画成同级。

**实测（2026-09-23 `COUNT(*)` / 抽样）**：
- 映射表 48,415 个 `名称` 中 **17,011** 个对应 **≥2 个不同 `型号`**。
- `EL300-2-07-SPFUS-00` → `Elite 300` + `Charger 2`（两行、两个型号）。
- `AC300-7-20-SPFJP-00` → `AC300` + `PV200` + `B300K` 等（储能与光伏同挂一个店铺 SKU）。
- `型号` 写在成员行上，不是 `名称` 的单值属性。

**与既有条目的冲突（已列清）**：
- ADR-034 playbook 把「店铺 SKU」与「NSSKU」画成型号下面的兄弟节点 → **错误，本条作废该画法**。
- ADR-032 / G-16「金额按型号上卷、路径不经 NSSKU」在多型号套件上**结构不成立**：不经 NS 就没有型号；经 NS 上卷金额又违反 G-18 / R-50。G-16 的「对外想按型号看金额」未废，**上卷路径作废**，多型号套件金额如何进型号维 **待对齐**。
- ADR-029 的 `MAX(型号)` 仍不生效，本条不复活。

**决策**：
1. **G-19**：商品维层级 = 店铺 SKU（`名称`）→ NSSKU（`成员货品`）→ 型号（NSSKU 行字段）。禁止店铺 SKU 与型号同级，禁止给店铺 SKU 直接赋一个型号。
2. **R-51**：型号只允许从 NSSKU 行读取。
3. G-18 仍有效（金额留在店铺 SKU）。G-17 仍有效（件数/路径拆 NS；NS 件数可再上卷到型号）。
4. 多型号套件的 **金额** 如何进入型号维 —— 本条不拍板。

**被否决**：店铺 SKU 与型号同级；从店铺 SKU 跳过 NSSKU 赋型号。

**影响**：`metrics.md` G-16/G-19；`rules.md` R-51；playbook 维度树；`data-sources.md`；`profile.yaml`；`errors/E-0007`；本条。不写代码。

## ADR-038 · 2026-09-23 · 单型号金额跟型号走；多型号进「套件未拆」

5. 型号维 ASP 因量价分叉 **待对齐**，本条不拍板。

## ADR-039 · 2026-09-23 · 无型号金额降级到唯一 NS；首期以主产品型号维为核心

**背景**：用户确认：主产品（储能 / 太阳能板）一般有型号，也会维护进 `产品型号度数范围`；配件周边（A- 开头 NS）不一一维护型号列，此情况下金额可以降级到 NS；配件识别规则后续再补。先以主产品为核心做初步落地和构建 agent。P- 开头一般是储能或太阳能板；Charger 系列虽为 A- 开头，会加型号，按主产品。

- G-18 / R-50 **不改**：金额仍留在店铺 SKU 行，禁止 JOIN 展开后对金额求和。降级的是上卷键，不是拆行。
- 上一问推荐的「未映射」桶：只留给 0 个 NS 的店铺 SKU（R-21）。有唯一 NS、只是没型号的，不再进未映射。

**决策**：
1. **G-16 第四档**：无型号且恰好 1 个 NS → 金额跟该 NS 走。无型号且 0 个 NS → 「未映射」。无型号且 ≥2 个 NS → 不拆金额、不进型号/品类；桶名本条不拍板（映射表 388 个名称）。

5. **前缀不是过滤器**：判别键永远是型号列。P- / A- 只作背景（COUNT @ 2026-09-23：P- 行 40,192 全部有型号；A- 行 10,370 中 3,905 有型号、6,465 无）。Charger 是 A- 但有型号，必须跟型号走。

**被否决**：无型号并进「套件未拆」；把无型号金额拆到多个 NS；用 A- / P- 前缀替代型号列做金额分流。

**未拍板**：型号占位值「配件」（84 个 A- NS）；≥2 个无型号 NS 的金额桶名；NS 维 ASP。

**影响**：`metrics.md` G-16/G-17；`rules.md` R-21 注记 + R-54；playbook；`data-sources.md`；`profile.yaml`；`data-audit.md` §14.9；`PROJECT_STATUS.md`。不写代码。

## ADR-047 · 2026-09-23 · 型号维 ASP 只对金额已进入该型号的单有效型号计算

**背景**：用户确认推荐：型号维 ASP 只对金额已经进入该型号的部分算（单有效型号）。套件未拆、未映射、配件降级到 NS 的，不出型号 ASP。站点 ASP 继续用 M102 / M104（店铺 SKU 件数）。

**冲突（已列清）**：G-16 把多型号金额放进「套件未拆」，G-17 仍把套件成员件数记到各型号。若用「该型号全部金额 / 该型号全部件数」会假造件单价。站点 ASP 用 M104，与型号件数不是同一套（ADR-045）。

1. **站点 / 店铺 SKU ASP** = M102 / M104（店铺 SKU 件数，R-30 v2）。不变。
2. **型号维 ASP** 只允许对**金额已进入该有效型号**的店铺 SKU 计算，即 G-16 单有效型号那一档。分子 = 这些行的净销售额；分母 = **同一批行**的 G-17 件数。禁止用该型号全部件数（含套件成员件数）作分母。
3. **套件未拆、未映射、配件降级到 NS**：不出型号 ASP；其金额与件数不得填入任何型号的 ASP 分子或分母。
4. NSSKU 维默认仍禁止 ASP（G-18）。本条不开配件 NS 维 ASP。

**被否决**：型号 ASP = 该型号全部金额 / 该型号全部件数；用站点 M104 当型号 ASP 分母；给套件未拆 / 未映射 / 降级 NS 出型号 ASP。

## ADR-060 · 2026-09-24 · 站点与市场两粒；site=EU 不是欧盟市场

## ADR-067 · 2026-09-24 · 核心与场景解耦：通用数分入口，月报只是第一份剧本

**背景**：用户确认改规划。担心按月报 playbook 施工会把产品做成单一经营分析 agent，无法覆盖用户行为、广告费用、SQL 编写等任意数分问题。ADR-032 已写「月报不是项目本身」，但 ADR-066 的 S0 只规划了 `harness --help`，探索入口拖到 S7，核心仍有被月报步骤焊死的风险。

**决策**：
1. **产品入口两个并列**：`run --playbook <id>` 跑已固化剧本；`ask <问题>` 跑探索（任意数分问题）。S0 两个命令都必须存在。
2. **编排器禁止写死月报**。剧本只经 registry 按 id 加载。禁止 `import` 月报正文、禁止硬编码月报章节或 playbook id。S0 合同测试必须用 **fixture 剧本**（不是经营月报）证明核心可跑第二条路径。
3. **Skill / Reporter / Memory 不得绑定月报**。Skill 必须能在 `ask` 或其它剧本下单独调用。报告大纲来自 `plan.md` / playbook，禁止写死经营月报六章。情节记忆按「同 playbook 指纹」检索，不是「上期月报」。
4. **后续场景以剧本包扩展**，不改编排器：用户行为、广告费用等在 playbook 注册表占位。无数据源时只许「无数据 / 口径待确认」，不许空转出数。广告接入槽已在 `ingest/ads/`。SQL 编写是 Tool + `ask`，不是月报的一章。
5. **月报仍是第一份验收剧本**（ADR-002 / ADR-032 不改）：用它压口径与证据包，不用它定义产品形状。
6. `ask` 在 S7 之前可以没有 LLM：无 key 时显式 no-op，并允许人工放入 `plan.md` 再执行（仍过 C1）。不得把 `ask` 做成 `run monthly` 的别名。

**被否决**：只做 `harness monthly`；编排器内嵌月报九步；把用户行为/广告先塞进月报章节；等 S7 才露出提问入口。

**影响**：`10-architecture.md` §8/§9/§11/§13；`rules.md` R-82；`playbooks/index.md`；skills 通用约定；charter；`profile.yaml`；`PROJECT_STATUS.md`。不写 `harness/` 代码。

## ADR-068 · 2026-09-24 · 跨平台 canonical 内核 + TikTok 首阶段真实接入

**背景**：用户明确产品后续须覆盖独立站、Amazon、eBay、AliExpress、TikTok Shop、迪卡侬等电商平台。复核发现现规划虽声明“通用 harness”，但规则、指标、评估、白名单和目录仍绑定 Shopify/月报；若直接开工 S0，会把平台差异焊进核心。经 19 轮单问题对齐，用户确认首阶段以 TikTok 真实数据作为第二平台验证，并要求官方口径像 Shopify 一样留档可溯源。

**实测与官方证据（2026-09-24）**：
- `bluetti_new` 已有 TikTok 销售、退货/退款、取消、Affiliate、LIVE 七张活表；退款表有 `event_date` 与金额，故无需新增外部退款源。
- TikTok `seller_sku` 166 个，现有 NSSKU 映射命中 158 个；两个 schema 排序规则不同，适配器须先规范化字符串。
- TikTok Seller Center 官方定义：GMV 按**支付时间**，包含取消与退款；Affiliate LIVE/Video GMV 有 14 天点击归因；2026 年销售归因升级为 Direct/Indirect + last-touch。来源：
  - https://seller-us.tiktok.com/university/essay?knowledge_id=813364865828654
  - https://seller-us.tiktok.com/university/essay?knowledge_id=6494954580231950
  - https://seller-us.tiktok.com/university/essay?knowledge_id=8670842792888078

**决策**：
1. **平台适配边界**：所有平台先经 `PlatformAdapter` 映射到统一 canonical 数据模型；Playbook、Skill、Metric、Reporter 默认只读 canonical，不感知平台表名。平台原生分析走显式 extension，不得绕过 adapter 直读。
2. **指标四态**：`canonical` 用于统一分析；`platform-native` 保留平台官方定义且不得跨平台直接相加；`provisional` 允许 `ask` 探索但必须留定义/SQL/快照并禁止进入正式报告；`diagnostic` 只用于质量与对账。provisional 经用户确认 + ADR 方可转 canonical。
3. **规则四层**：`core / domain / platform / playbook` 按 scope 组合加载。现有 Shopify 表白名单、退款、商品映射规则移入 Shopify platform pack；月报时间窗、章节与审批规则移入 monthly playbook pack，禁止全局误伤其它场景。
4. **机器可读注册**：Playbook 必须有 manifest（id、contract_version、steps、metric_refs、skill_refs、rule_packs、required_capabilities、time_scope、outline、approval_policy）；Markdown 只作人读说明。Registry 禁止解析 Markdown 生成执行计划。
5. **平台能力矩阵**：每个 adapter 声明订单、退款、客户、流量、广告、目标、Affiliate、LIVE 等 capability 与覆盖期。缺能力不得估算；未对齐映射进入 `awaiting_alignment`，每次只问一个问题。受影响分支暂停，其余分支可留证据；阻断项关闭前不得发布正式报告。
6. **指标与审批注册**：新增 `MetricPort / MetricRegistry`，计算器只按 metric id 解析实现。审批复用指纹至少包含组织/profile、playbook manifest、metric/rule pack、adapter/schema、SQL 模板与数据源版本；改任一项必须重审。
7. **身份与租户隔离**：客户身份默认按平台/店铺命名空间隔离；只有经确认的身份映射表才允许跨平台合并。平台官方定义可全局共享，业务口径、映射和审批只在当前组织/profile 复用。
8. **TikTok 首阶段接入**：首阶段真实接入七张权威表：`tiktok_sales_by_order`、`tiktok_returns`、`tiktok_return_items`、`tiktok_cancellations`、`tiktok_cancel_items`、`tiktok_affiliate_orders`、`tiktok_live_performance`。`tiktok_sales_by_order_0731`、`tb_tiktok_tableau`、`vw_tiktok_tableau` 不作为 canonical 源。
9. **TikTok canonical 映射**：M101/M102 继续遵守已确认的**下单时点**，取 `created_time`；TikTok 官方按 `paid_time` 的 GMV 仅作 platform-native。样品单筛除；取消单筛除且取消退款不得二次冲减；赠品记录保留并单列但不进 M101–M106；退货按 `tiktok_returns.event_date` 冲减 M102，商品归因用 `tiktok_return_items`。商品退款取 `refund_subtotal`，不把运费/税并入商品净销售额。
10. **TikTok 商品映射**：未映射 SKU 仍计入平台与跨平台总销售，在 NSSKU/型号/品类拆解中进入“未映射”桶，并同时展示 SKU 覆盖率与金额覆盖率。
11. **首阶段报告**：经营月报采用“跨平台 canonical 总览 + Shopify/TikTok 分平台章节 + platform-native 附录”。TikTok Affiliate/LIVE 首阶段作为只读原生模块，先核官方口径与归因窗口再启用，不参与 canonical 合计。
12. **官方口径留档**：TikTok 当前可见的销售、订单、件数、退款、样品、Affiliate、LIVE 等官方定义均登记来源 URL、适用地区、检索日期与实现状态；只有字段和数据核验通过者标“可实现”，其余标“已登记未启用”。
13. **PII 默认拒绝**：买家昵称/用户名、收件人姓名、电话、地址及含 PII 的 `raw_json` 禁止进入 canonical、trace、证据包和报告。客户分析只用“平台命名空间 + 不可逆哈希”标识；原始 PII 访问须单独授权。
14. **多平台完整度**：每个平台独立快照、hash、水位与 completeness。任一必需平台未到报告截止时间，只能生成标明逐平台覆盖率的 `partial`；全部到齐后生成新 `final`，禁止沿用上期数据补齐或覆盖旧版本。
15. **生产运行契约补齐**：S0 同时冻结 Run 状态机（含 `awaiting_alignment`、取消、恢复、幂等）、逐源 Artifact Envelope、`ErrorEnvelope`、Tool capability、SQL AST 只读校验、trace 脱敏 schema、配置 schema/version/migration。R-81 被本条收窄：稳定 Port + 注册类型 + no-op 必须先在，但不为每个未来平台盲建空目录。

**被否决**：Playbook 直读平台表；把 TikTok GMV 当 canonical M101/M102；规则整包全局加载；遇到映射缺口静默跳过；跨组织复用业务口径；用当前状态近似退款；把 Affiliate/LIVE 并入跨平台合计；所有预留能力都铺空目录。

**修订关系**：扩展 ADR-009/015/066/067；首阶段平台由“仅 Shopify”修订为“Shopify + TikTok”；ADR-027/028 的“8 张表”收窄为 **Shopify platform pack 白名单**，不再是 harness 全局白名单；ADR-049 的 `order_name` 收窄为 Shopify adapter 键，canonical 订单键由本 ADR 定义；R-41/R-81 已据此修订。未写 `harness/` 代码。

**影响**：`00-charter.md`、`10-architecture.md`、`metrics.md`、`data-sources.md`、`data-audit.md`、playbooks、skills、`rules.md`、`eval-rubric.md`、`profile.yaml`、`PROJECT_STATUS.md`。

## ADR-069 · 2026-09-24 · 动态平台 Playbook + 生产契约冻结

**背景**：ADR-068 已确立跨平台 canonical，但复核发现 S0 前仍有七类返工风险：月报规则残留 Shopify `sale_date`；Run 状态与 partial/final/正式等级混用；C3 先于证据包封存；Playbook/Rule Pack/Plan DAG 缺机器契约；退款 adjustment 无 canonical 类型；平台能力只在人读文档里分层；审批指纹未明确口径内容。用户要求逐项问答至可完整修复，经 17 轮单问题确认如下。

**决策**：
1. **报告三层严格隔离**：`draft` Profile 只可 `dry_run`；active Profile 在所选必需平台水位未齐时可经 C3 发布 `formal_partial`；全部必需平台齐备方可 `formal_final`。任何未关闭的业务口径对齐禁止正式发布。
2. **Playbook 不写死平台组合**：经营月报声明 `platform_selection=explicit`。每次交互式 Run 必须显式给出 `target_platforms`；定时任务必须在调度配置中声明。用户可复用同一月报 Playbook 选择 Shopify、Amazon、TikTok 或其它已注册平台，无须复制 Playbook。
3. **本次目标决定必需平台**：`target_platforms` 中的平台是该 Run 的 required platforms；Profile `enabled` 只表示可选择。核心能力缺失时不得在原目标范围内 final；用户可明确移出该平台，整体 C1 重新审核后为剩余目标生成 final。
4. **能力分核心与可选**：月报核心商业总账能力为订单/行项、商品金额与折扣、币种与汇率、下单时间、取消识别、退款金额与发生时间、稳定账户/订单键、数据水位。商品统一映射、客户、流量、目标、归因、退货件数和平台原生模块均为可选能力。
5. **可选能力不得静默跳过**：发现 unsupported 时先逐项询问用户。能补则该分支进入 `awaiting_alignment`；用户明确本次无法提供并同意跳过后，记录 run-only waiver，在能力矩阵标注并省略对应章节，仍可 final。长期关闭必须另行明确并更新 Profile/ADR。
6. **无人值守不代替用户决策**：定时 Run 遇到新的能力缺口时生成 alignment ticket 并通知用户；未受影响分支继续形成 dry-run，禁止自动跳过或正式发布。
7. **待对齐只允许 dry-run**：受影响分支暂停，独立分支继续计算和留证据；可生成带水印的内部 dry-run，但不得进入 C3 或 formal 发布。
8. **平台账户是 canonical 经营原子**：统一键为 `platform + account_id`；Shopify site、Amazon seller+marketplace、TikTok shop 先保持独立，再由 Profile 映射到 reporting site/market/region。缺市场映射不影响总账，但相应汇总维度按可选能力流程对齐。
9. **组件级审批复用**：平台组合变化后整体计划 C1 必须重审；未变化平台且口径/SQL/source contract 指纹完全相同的 C2 分支可复用；新增平台分支单独 C2；C3 每份报告每次审核。
10. **审批口径指纹确定化**：`caliber_fingerprint` 必须覆盖当前 metric 定义、有效 rule-pack 内容、manifest、Profile、adapter/schema contract、SQL 模板、source contract 及所有会影响结果的 env override；敏感值只入 hash，不落明文。
11. **数据齐备判定**：每个核心源按报告期截止点 + Profile/adapter 声明的延迟窗口检查 watermark 和质量断言。迟到数据生成新版本，禁止覆盖旧版。报告期内任何有效金额无法按既定汇率规则折算时，阻断跨币种 formal 发布；禁止排除或邻近月/实时汇率兜底。
12. **Profile 与 Adapter 分级认证**：Profile 经过完整校准 Run、核心合同/对账/Eval 通过并由用户或管理员显式批准后，以新不可变版本转 active。新增 Adapter 按组件认证；未通过合同测试、样本对账与批准的 adapter/version 只能 dry-run，不使已认证组件退回 draft。
13. **地区原生口径门禁**：TikTok 非美国地区在对应官方定义核验前保持 platform-native 未启用；canonical 订单/退款可正常进入正式报告。禁止拿美国定义加提示后当其它地区正式原生口径。
14. **机器契约先于 S0 实现**：S0 必须冻结 Playbook manifest、Rule Pack 索引、Plan DAG、Metric availability、Run/Error/Artifact/Trace envelope 与 Profile schema/migration。`awaiting_alignment` 是分支状态，Orchestrator 不得退化为线性流水线。
15. **C3 审核不可变候选包**：运行过程持续写临时工件；执行与校验完成后封存候选证据包并计算 hash；Evaluator 读取该候选包；C3 通过后只写发布记录/签名并发布，不修改候选内容。C3 驳回后的修复形成新 revision/hash。
16. **canonical 最小补强**：报告期只认 canonical `order_created_date`，物理时间字段留在 adapter；退款事件增加 `refund_kind`（至少 line refund / order adjustment），退款数量可空并由 capability 声明；订单行增加商业行/样品/赠品标记。Shopify adjustment 与 TikTok refund 不得靠同一无类型字段猜语义。

**被否决**：按平台组合复制月报；所有 enabled 平台自动阻断所有场景；缺可选能力静默跳过或补 0；核心能力缺失仍保留平台并发布 final；跳过确认自动永久写入 Profile；新增平台使整个 Profile 退回 draft；自动继承 active；美国站原生口径直接套其它地区；C3 审核后再补写证据包；月报 SQL 在跨平台层写死 `sale_date`。

**修订关系**：扩展 ADR-013/057/066/067/068；将 ADR-055/059/065 中的 Shopify 物理时间字段收窄到 `platform:shopify`，跨平台规则统一使用 canonical 时间；不改变 ADR-010 的下单时点业务口径。

**影响**：`10-architecture.md`、`metrics.md`、`data-sources.md`、playbooks、`rules.md`、`eval-rubric.md`、`profile.yaml`、`PROJECT_STATUS.md`。本条不写 `harness/` 业务代码。

## ADR-070 · 2026-09-24 · S0 实现就绪契约校正

**背景**：ADR-069 后的独立实现就绪复核发现，人读说明与机器 manifest 仍有字段名、审批顺序、状态、评估 overlay、错误归档条件和指纹字段漂移。另有 M104 文案误写为退货发生月冲减，与 ADR-010“退款单件数保留在原下单月”冲突。本条只校正既有决策的实现表达，不新增业务口径。

**决策**：
1. Playbook 能力分类字段统一为 `core_capabilities` / `optional_capabilities`；平台 Profile/Adapter 只声明扁平 supported/unsupported capability，核心/可选分类由当前 Playbook manifest 决定。
2. 执行顺序统一为：目标选择与无数据 preflight → 物化计划 → C1 → 生成/归档原料 SQL → C2 → 快照与 adapter → 计算 → 校验 → 渲染 → 封包 → 评估 → C3/发布。C1 前禁止读取业务数据，C2 前禁止执行原料 SQL。
3. `run_status` 增加规划与 SQL 准备状态；`awaiting_alignment` / `waiting_data` 是分支暂停态，只有无可运行分支时才提升为 Run 暂停态。幂等键统一包含 `plan_revision`。
4. Plan step 的公共必填字段为 `step_id/type/depends_on/platform_scope/input_fingerprint`；capability、metric、rule-pack 与 unsupported 策略仅在适用 step 必填，不用空值伪装。
5. Eval overlay 使用 manifest 中的机器 id，并在量表中逐一登记；M106 按账户 ASP 与商品/型号 ASP 分能力门禁。
6. 所有阻断运行失败必须产生 `ErrorEnvelope`；只有可复发的新错误家族、架构/口径缺陷或需要防回归门禁时才新增 E-NNNN。
7. M104 按 ADR-010 恢复为下单月商业售出件数，退款件数不冲减 M104，只用于 M207b；缺 `return_quantity` 不影响核心 M104。
8. C1/C2 指纹字段按 ADR-069 完整化；C1 的 caliber 使用可在 preflight 解析的 SQL 模板注册契约 hash，C2 另审实际 `rendered_sql_hash`；Profile、manifest 与架构使用同一字段集合，并显式包含 adapter schema fingerprint。
9. 跨模块接口归 `contracts`，canonical schema 是允许被 adapter/metric/validator 依赖的稳定数据契约；新增 `RunStateStorePort` 与 `ConfigPort` 明确运行状态/checkpoint和不可变配置归属。
10. S0 的 echo fixture、机器 schema、no-op 矩阵和依赖边界测试属于 S0 首刀交付，不在开工前伪造“已完成”文件。

**被否决**：边写 S0 边猜字段；C1 前先查业务数据；所有失败都创建 E-NNNN；把 profile capability 再复制一份核心/可选分类；缺 TikTok 退货数量就禁用 M104；为通过严格加载器给所有 step 填无意义空字段。

**修订关系**：只澄清 ADR-010/066～069 的实现契约；不改变业务口径与平台范围。

**影响**：`10-architecture.md`、`metrics.md`、playbooks、skills、`rules.md`、`eval-rubric.md`、`data-sources.md`、`profile.yaml`、`PROJECT_STATUS.md`。本条不写 `harness/` 业务代码。
