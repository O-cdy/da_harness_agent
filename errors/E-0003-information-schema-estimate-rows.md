# E-0003 · 用 `information_schema.table_rows` 估算值当实测行数（复发 4 次，已升级为硬规则）

| 字段 | 内容 |
|---|---|
| 编号 | E-0003 |
| 发现日期 | 2026-09-22 |
| 模块 | ingest / 数据源盘点 |
| 状态 | fixed（已升级为硬规则 R-36） |
| 关联 ADR | ADR-026 |
| 关联规则 | **R-36** |

## 1. 现象

同一张表的行数，估算值与 `COUNT(*)` 相差巨大，三次分别踩中：

| 表 | `table_rows`（估算） | `COUNT(*)`（实测） | 偏差 |
|---|---|---|---|
| `nssku对应映射表` | 66,144 | **73,858** | +11.7% |
| `exchange_rate` | 911 | **1,169** | +28.3% |
| `shopify_customers_by_site` | 1,867,503 | **2,229,529** | +19.4% |
| `shopify_sales_by_order` | 1,224,072 | **1,289,508** | +5.3% |
| `shopify_customers_by_site`（第 4 次，2026-09-22 19:40） | 1,867,503 | **2,229,529** | +19.4% |
| `repurchase_user_sku_stats`（误记，非估算） | 491,042 | **495,875** | — |

早期登记的口径事实（如「NSSKU 66,144 行」「客户表 186 万行」）因此全部失真。

## 2. 触发条件

InnoDB 表的 `information_schema.tables.table_rows` 是**采样估算值**，不是精确值；
只要表在被并发写入或统计信息未刷新，偏差可达 10%~30%。

## 3. 根因

- 表象根因：把估算值当实测值写进口径文档。
- **架构根因**：缺少「口径数字必须来自精确查询」的硬约束。估算值读起来更快、写起来更省事，
  因此在没有规则约束时必然被反复误用。

## 4. 最小复现

```sql
SELECT table_rows FROM information_schema.tables
  WHERE table_schema='shared_data' AND table_name='exchange_rate';   -- 911
SELECT COUNT(*) FROM shared_data.exchange_rate;                      -- 1169
```

## 5. 修复

- 所有写进口径文档 / 核验记录的行数改为 `COUNT(*)` 实测值；
- `data-audit.md` §8 白名单表全部标注实测规模；
- `rules.md` 新增 **R-36**：「行数一律以 `COUNT(*)` 为准，`information_schema` 估算值不可用于口径判断」。

## 6. 防回归门禁

- **R-36（硬规则，阻断级）**：任何口径判断、容量评估、覆盖率计算，行数必须来自 `COUNT(*)`。
- 后续新增数据源登记时，`data-audit.md` §8 白名单表必须填实测值。

## 7. 复盘备注

**复发 4 次**（NSSKU / 汇率 / 客户表 / 客户表再次），按 `errors/index.md` 第 4 条已**升级为硬规则 R-36**。
这是本项目第一个由错误复发升级而来的硬规则，可作为「错误 → 规则」转化路径的样板。

**第 4 次的特殊性（2026-09-22 19:40 巡检发现）**：这次踩坑的不是别处，正是 **R-36 自己要求的产物**
—— `data-audit.md` §8 的「权威表白名单」。白名单里 `shopify_customers_by_site` 登记的仍是估算值
1,867,503，`repurchase_user_sku_stats` 误记为 491,042，`产品型号度数范围` 在 `data-sources.md` 中误记为 204。

→ **规则只写「要用实测值」不够，还必须要求「登记实测日期」**，否则无法事后分辨哪些数是实测、哪些是抄的。
R-36 已追加该项；§8 白名单已全部标注 `@ 2026-09-22 19:40 重跑`。
